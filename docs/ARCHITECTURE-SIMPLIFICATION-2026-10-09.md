担当: Claude。所有者との相談で決まった方針の記録。コード・本番設定・DB・課金は変更していない。設計判断は所有者から一任された（「あなたに一任します」）。

最新指示: [10/10のLinux移行・Cloudflare無料化計画](SURFACE-SERVER-TRIAL-2026-10-10.md)を優先する。複雑さの解消を第一に、Linuxノートへ本体を集約しCloudflareを公開入口にする準備を並行する。下のVercel入口・同じURL・クラウド認証維持は10/9時点の旧案であり、最終構成を固定しない。停止中は閲覧のみ・端末内送信待ちなし・拒否の検証前に書戻しを撤去しない方針は維持する。

## 所有者の決定と前提

1. クラウドサービスへの課金は避ける。重い処理はローカル（本番PC）へ寄せる。
2. このPCは本番サーバーとして扱う。「個人用PCをやめる」系の案は採らない。
3. PC停止時の予備は残す。ただし**予備では書き込みを受け付けない（閲覧のみ）**。
4. 端末内に保存して復帰後に送る方式（オフライン送信待ち）は、複雑化を避けるため採らない。2026-10-02の「オフライン下書きは不採用」を維持する。
5. AIがアクセスする範囲から個人情報を外す方向で検討する。実データが必要な作業はローカルLLMを候補とする。

## 10/9時点の構成案（公開先は10/10計画を優先）

[PC集約](PC-COMPUTE-UNIFICATION-2026-10-08.md)（Codexが作業中）の構成を基本とする。公開URL `https://tuat-tf.vercel.app` を維持し、Vercelの入口からWorkerを経てPCのNextへ送る。PC停止時はVercel予備へ送る。独自ドメインや`workers.dev`の新URLへの移行案は、URL維持の指示と再ログイン・PWA再追加の負担があるため採らない。

この構成に対して、決定3で次を変える。

| 項目 | 変更前の想定 | 今回の方針 |
| --- | --- | --- |
| 予備（クラウドDB・Vercel予備）での保存 | 停止中も受け付け、復帰時にPCへ書き戻す | 受け付けない。画面で「サーバー停止中のため保存できません」と示し、DB側でも拒否する（UIだけに頼らない） |
| 同期 | 双方向（`cloud-mirror`の書き戻し、競合保護、`failover_changes`） | PC→クラウドの一方向だけ |
| 復帰時の作業 | 書戻しの照合 | なし。PCが正本のまま |
| ログイン | クラウドSupabase | 変更なし。予備時もそのまま使える |

理由: 構成で最も複雑で、検証の負担が大きいのが停止中の書込みと書戻しである。停止はまれで、記録は復帰後に入力できる。閲覧のみにすれば、書戻し・競合・二重受付の問題がなくなる。

### 受入条件

- 通常時: 現在と同じURL・ログイン・権限で、閲覧・保存ができる。
- PC停止時: 停止判定の後、予備で直近同期時点のデータを閲覧できる。保存操作は明示的に失敗し、成功と誤認させない。停止判定前に送られた保存の結果が不明な場合、予備へ再送しない。
- 復帰時: 書戻しなしで通常に戻る。予備に書込みが残っていないことを確認できる。
- 停止中は定期処理が止まる。復帰後はjournalに従い、結果不明のものを再送しない（既存方針どおり）。

### 撤去の順番（実装時）

1. 予備側の書込み拒否を、UIとDBの両方で入れて検証する。
2. 書込み拒否が本番で有効になったことを確認してから、`cloud-mirror`の書戻し部分、書戻し失敗行の保護、`failover_changes`・`zz_log_failover_change`の新規付与を停止する。既存のデータ・状態ファイルは、撤去計画を確認するまで削除しない。
3. AGENTS.md・PC本番運用の、書戻しに関する規則を更新する。

PC集約の本番切替や、Vercelの設定・プラン変更（Hobby化を含む）は、従来どおり具体的な内容ごとに所有者の承認を得る。

## AIの取扱範囲（提案・未実施）

現状は、本番DB（WSL `Ubuntu`）と`.contingency/`の秘密情報が、AIの作業するOSユーザーから読める。規則だけでなく、技術的に境界を設けることを提案する。

| 対象 | AI |
| --- | --- |
| リポジトリのコード・文書 | 可 |
| 開発用DB（合成データのみ。既存の独立レビュー環境の合成`@example.invalid`データを流用候補） | 可 |
| 本番の状態確認（`status.mjs`・`audit-backend.mjs`など、個人情報・秘密値を出力しないもの） | 可 |
| 本番DBの行・バックアップ本体・`.contingency/`の秘密値・ログイン済み本番画面 | 不可 |
| 本番のmigration・データ操作 | AIはスクリプトとdryRun手順の作成まで。適用は所有者 |

段階:

1. 規則として上記をAGENTS.mdへ追加する（所有者の確認後）。
2. AI作業用のWindowsユーザーを分ける。WSLのディストリビューションはユーザーごとのため、本番DBに届かなくなる。`.contingency/`は本番側ユーザーだけ読めるようACLを設定する。管理者権限が必要なので所有者が実施する。
3. 実データが必要な分析・調査は、所有者がスクリプトを実行し、集計結果か個人を特定できない形だけをAIへ渡す。それでも本文が必要な場合に限り、ローカルLLMを使う。ローカルLLMは本番と同じPCで動くため、応答が遅くならないか確認してから導入する。

注意: 段階2の後は、AIが本番の定期処理・journalの復旧などを直接行えなくなる。現在Codexが担っている本番作業の手順を、所有者が実行する形へ移す必要がある。
