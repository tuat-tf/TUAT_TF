# 作業別の詳細規則

現行AGENTSの詳細を2026-10-09に分離し、2026-10-20の文書統合でPC集約後の構成へ更新。新しい承認は追加していない。作業に該当する節だけを読み、個別の最新指示・終了追記を照合する。コードがあることを公開済みとみなさない。

## 厳守ルール

- `origin/master`を基準にする。作業前に既存の変更・未追跡ファイルを保全し、`git pull`で最新化する。独立worktreeは最新の`origin/master`を取得して始める。diverge時は他人の変更を丸ごと取り込まず、自分の差分を載せ直す。force-pushは禁止。
- 既存の変更を戻さない。独立したローカル作業は担当ファイル・worktreeを分け、本番DB・環境変数・デプロイの変更は同時実行せず担当を一本化する。同名ローカルDBを本番PCの代わりに検証したことにしない。
- 作業ブランチはGitHubへpushしない。関連修正と記録をまとめ、検証後にmasterへ入れるときに1回だけpushする。小さな修正ごとのpushは避ける（2026-09-27確定）。
- 文書だけの変更は手元に保持し、次のコード変更と一緒にpushする。文書更新だけを理由にビルド・デプロイしない。ローカルで終了し、pushを保留したことを報告する。
- Vercel設定（Ignored Build Step・ブランチのビルド停止等）は具体的な変更についてオーナー承認を得る。ビルド代削減方針への同意を設定変更の承認に流用しない。過去の使用量・残額は現在値として扱わない。
- migrationは新しいタイムスタンプで追加し、冪等にする。適用対象・既存履歴・変更内容を確認する。本番初回のmigration・同期・一括更新の前に、対象テーブルのスナップショットとdryRunによる差分確認を必ず行う。
- 公開リポジトリへ秘密値、実ユーザーのデータ退避、未解決の攻撃手順を入れない。秘密値をログ・報告へ出さない。
- コミットの末尾に作業したエージェント自身の`Co-Authored-By`を付け、他AIを名乗らない。Codexは`Co-Authored-By: Codex <noreply@openai.com>`。

## 完了の定義

2026-10-04の全体品質改善では、所有者の新しい指示により本番反映を保留し、本人用検証を先行する。以後も修正のたびにmasterへ反映せず、検証した変更をまとめて公開する。本人用環境は別origin・セッション・DBとし、ログイン等で本番へ合流する構成や本番データを共有するだけの別URLを隔離環境と呼ばない。根拠と進捗は [全体品質監査](APP-QUALITY-AUDIT-2026-10-04.md)。

コードの本番反映は、以下まで確認して完了と報告する。文書のみの場合は上記の保留運用を適用する。

1. `npm run check:environment`で環境差を確認し、`npx tsc --noEmit`・対象eslint・`npx vitest run`を通す。`npm run build`はpush直前に行う。必要な運用テスト・dryRun・UI確認も済ませる。本番稼働中の依存を消さず、必要なら検証用環境を分離する。
2. ローカルの作業ブランチ・worktreeで関連する変更と記録をまとめる。作業ブランチはpushしない。
3. `git fetch origin master`後、masterへfast-forwardして1回だけpushし、`master -> master`を確認する。ff-onlyにならなければ最新の`origin/master`上に自分の差分を載せ直して検証する。force-pushしない。
4. 更新対象のPC releaseが自分のcommitへ固定され、公開`/api/version`のSHAと一致することを確認する。Vercel側も更新する場合はProductionの成功を確認する。Vercel MCPの`list_deployments`を使い、`target: production`・`state: READY`・`meta.githubCommitSha`の一致を見る。`target: null`のPreviewでは完了ではない。公式GitHub deployment statusを使う場合もProductionの成功と公開`/api/version`のSHA一致を確認する。ビルド中は待ち、失敗は修正する。確認経路が使えず証拠が得られない場合は、その旨を伝えてオーナーに確認を依頼する。
5. commit、masterへの反映、PCと更新対象の公開入口の状態、検証範囲を報告する。iOS PWA・Android等の実機未確認を、ブラウザ合成テストの成功で代替しない。

途中でオーナー判断などが必要になったら、進めた範囲と本番反映の有無を明示する。ブランチ止まり・未適用migrationを本番完了と報告しない。

## 実装の基本

- 修正前に問題の操作を再現し、期待と実際・原因を確認する。再現できない場合は推測と未確認を明示し、原因を断定して修正しない。
- 実装前に、利用者・目的・入口から終了までの受入条件と、保持するデータ・権限・失敗後の復旧条件を短く記録する。既存ルールとコードから判断できる条件は担当が整理し、利用者へ仕様作成を丸投げしない。
- 検証は実装の構造ではなく受入条件から選ぶ。関数・画面単位の成功だけでなく一連の操作を確認し、AIが置いた人数制限・初期値・自動処理等の前提自体も検証する。結果不明の保存を無条件で再送しない。
- 修正に不要な機能・設定・警告・確認画面を増やさず、既存の共通部品を使う。検証で既存修正の有効性が確認できた場合は作り直さない。
- 行数・見た目の好みだけで分割・統合・全面再構成しない。独自の状態管理・キャッシュ・共通層・操作を追加する際は利用者の問題と既存方式では足りない理由を記録する。規則に沿う通常修正は担当が判断し、確認を繰り返さない。
- 取得失敗を0件・未登録・404へ変換しない。件数上限と後段の絞り込み・集計で対象を欠落させない。未保存・部分保存・競合・再試行の受入条件を確認する。
- 完了報告は、できるようになった利用者の操作、その確認方法、残る未確認と本番反映を先に示す。テスト件数・ビルド成功・Production成功を使い勝手や実機運用の証拠にしない。根拠は [実装品質の改善方針](IMPLEMENTATION-QUALITY-2026-10-04.md)。
- Next.js 16 App Router / React 19 / Tailwind v4 / Supabase。NextのAPI・規約は学習時と異なり得るため、コードを書く前に`node_modules/next/dist/docs/`の該当ガイドを読む。`params`・`searchParams`・`cookies()`はawait、入口は`src/proxy.ts`、Tailwindの定義は`globals.css`の`@theme`。
- 初期データはServer Componentと`src/lib/queries/`（公開入口`@/lib/queries`）へ集約し、画面に直接Supabase取得を散らさない。操作系はClient Component。互いに依存しないDB取得を直列に積まない。
- `getCurrentUserId()`はセッションのID取得でDBを読まない。`getCurrentProfile()`はプロフィール・ロールをDBから読む。Reactのリクエスト内キャッシュと「DB取得なし」を混同しない。
- 本人IDと権限の根拠は検証済み`getClaims().claims.sub`または`getUser().user.id`とする。cookie内の`session.user`を本人情報として信用しない。プロフィール・ロールの照合IDも検証済み本人IDへ一致させ、proxyの認証だけに依存するサーバー側の認可を作らない。
- UI権限は`permissionsOf(profile.roles)`、DBは`can_*()` / `is_admin()` / `is_staff()`によるRLSで守る。`profile_roles`×`roles`の複数ロールをORで判定する。UIだけを変えて権限を広げない。
- RLSで拒否されたupdate/deleteがエラーなし・0件になる場合がある。重要な更新は`.select()`等で対象件数を確認し、必要な認証更新・安全な再試行後も0件なら明示エラーとする。0件削除を成功にしない。
- 学年は`B1/B2/B3/B4・M1/M2・D1/D2/D3`、`gradeShort` / `GRADE_OPTIONS`を使う。
- UIと部員向け文言は[UI統一](UI-UNIFICATION.md)・[文言規約](WORDING-GUIDELINES.md)を参照する。入力は全画面、選択はシート、編集・削除は共通の「…」メニューを基本に、現在の共通部品を使う。
- `cacheComponents`・`experimental.staleTimes`はiOS PWAの実障害を受けて再導入禁止。PullToRefreshを方式変更だけで復活させない。東京リージョン`hnd1`・画面のReact Queryキャッシュ・`loading.tsx`を維持する。FreezeProbeの診断記録を保ち、削除済みのTab Labを戻さない。
- ガラスUIは全員の標準表示。初回SSR・loading・一般部員プレビューも同じ表示を使い、旧版への切替設定は戻さない。2026-10-03の初期off/端末opt-inは過去の判断。実装・検証状態は[UI統一の改善](UI-UNIFICATION-2026-10-05.md)と対象作業の終了追記で確認する。個別の[OB戦等の反映記録](OB-MEMBER-PRODUCTION-2026-10-05.md)を別の全体品質改善の公開承認へ流用しない。
- 下部タブ背景は2026-10-02に直接透過へ統一済み。過去の背景画像化・vendor読込・WebGL制約を現行の要件として戻さない。ガラスを全操作へ広げず、いいね・コメント等は装飾を抑えた現在の方針を維持する。

## 認証・本番PC・予備構成

主系はPC内の暗号化WSL領域のアプリ・通常DB・認証・画像で、公開入口はCloudflare。旧Vercel URLとPC外の暗号化バックアップは残る。操作前に[PC本番運用](../ops/laptop/PC-PRODUCTION-HANDOFF.md)の最新注記と[集約作業記録](PC-LOCAL-AUTH-IMAGES-2026-10-12.md)の終了追記を読む。旧構成の説明や候補コードだけを現行の手順にしない。

- 本人IDを維持したPC内認証と`getClaims`による本人確認を保つ。一時的な認証・通信失敗だけで有効なcookieを消してログアウトさせない。SessionKeepAliveとリダイレクト時のcookie引継ぎを維持する。
- 旧PC/cloud source fence、旧cloud Data API off、旧relay retired503、旧Windows backend disabled、旧Jobs config=falseを維持する。旧queueの再送、業務mirror、予備への書込み、復帰時の書戻しを再開しない。Google Drive連携は廃止済み。
- 新しいmigrationは実正本・現在の履歴・RLS・定期処理との依存を確認する。旧構成を根拠にクラウドへ同時適用したり、failover用triggerを一律追加したりしない。保存してある旧履歴・mirror-state・未解決操作は消さない。
- DB・認証・画像を含む15分ごとのcombined backup、PC外への暗号化保存、読戻しによる完全性確認、別DBでの復元検証を保護する。host/Jobsは同じgeneration・DB identity・新しいreceiptを確認する。35分のbackup期限や120秒の心拍条件を削除して保存を通さない。
- 定期処理は同じNextへ接続するshared-pc Jobsへ集約する。記録・大会・期限切れ整理に加え、明示的に有効なlocal Pushを扱う。既存の`stateDirectory`・`activateAt`・journalと結果不明/失敗履歴を保ち、同じ枠を再送しない。詳細は[Jobs](../ops/pc-jobs/README.md)。
- 旧DB/Vercel cronの停止と、予定自動同期の取りやめを維持する。新旧の定期処理や手動同期を重複実行せず、プロセス起動だけでなく処理結果と次回実行可能性を確認する。
- 計画的にappを停止する前には正式監視と独立した保全監視を維持する。正式監視の終了でWSLサービスやmountが失われる場合がある。WSL/DB、保護mount、`D:\TUAT_TF\node_modules`、旧`.contingency`を保全し、全Node終了・WSL停止・Docker volume削除を検証準備にしない。
- 移設・復旧では[移設手順](../ops/laptop/SERVER-HANDOFF.md)・[クラウド復帰条件](../ops/laptop/RETURN-TO-SUPABASE.md)も最新の主系構成と照合する。古いURL/envへ戻すだけで復旧済みとせず、正本・本人ID・画像・未解決操作・バックアップを確認する。旧writerの再有効化を通常の復旧に含めない。
- 本番と別のDBや合成環境だけを試して、実PCの復旧・OS再起動・定期処理・バックアップ・実機PWAを確認済みと扱わない。未確認は最新記録へ残す。
