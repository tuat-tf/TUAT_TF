# ノート・投稿フォームのUI統一（2026-10-05）

担当: Codex。全体UI改善のうち、ノート記事の展開・共有・管理と、つぶやきのストーリー・投票追加を担当します。本番反映は保留し、既存のローカル変更を保持します。

追記: 同日、所有者の訂正により、ノートの共有と管理は単一の「…」へ統一しました。下記の共有分離に関する記述は作業時点の履歴です。最新の受入条件と検証結果は[ノート操作の訂正記録](UI-NOTES-REVISION-2026-10-05.md)を参照してください。

## 着手時の確認と受入条件

- ノート記事一覧は、タイトル、共有、管理の「…」、独立した展開ボタンを同じ行に配置していました。共有と管理はコード上の操作は分かれていますが、ガラスUIで操作が44pxへ拡張され、共有と管理の間に余白がなく、記事名の表示幅も圧迫します。修正前の合成データをChrome・WebKitの320px幅で表示し、共有と管理の間隔が0pxになることと、長い記事名が本文より高く折り返される表示を再現しました。実機で報告された重なりは未確認です。
- 記事を読む操作は記事名の行へまとめ、共有・管理は別の操作行へ置きます。狭い幅や長い記事名でも、展開と共有・管理のタップ領域が重ならないこと、開閉で操作位置が動かないことを確認します。
- 共有はリンクのコピー・他アプリへの共有、管理は既存の編集・ピン留め・削除に限定します。公開前の共有不可、管理権限、削除確認を保持します。
- つぶやきフォームは「＋」から独自の選択行でストーリー・投票を切り替えていました。ストーリーの有無を共通Toggleで直接選び、投票追加を共通Buttonで見つけられるようにします。投票の入力・追加・解除もノート記事と同じ共通部品へ寄せます。
- 本文、引用、画像、投票設定、メンションを保持し、ストーリー解除時の画像解除、24時間での非表示、二重送信防止、結果不明時の確認手順を維持します。DB・認証・保存処理は変更しません。

## 検証・終了記録

- 記事名の行全体を単一の展開入口とし、共有と管理は別の操作行へ分けました。共有と管理は44pxの領域と8pxの間隔を確保し、管理メニューの名前もフォルダ・記事に合わせました。展開後には記事詳細への既存リンクを常に置き、省略した記事名も詳細で読めます。
- 共通UI担当の修正で、見出し・段落共通の`text-wrap: pretty`が`truncate`の折り返し禁止より優先される問題と、SubHeaderの右側操作が中央タイトルへはみ出す問題を修正しています。本担当も、その共通修正を含む表示で確認しました。
- ストーリーはフォーム本文に常時ある共通Toggle、投票追加・選択肢追加・解除は共通Buttonへ統一しました。投票の選択肢を共通Inputにし、2件の時も削除ボタンの領域を維持して、3件への追加時に入力幅が変わらないようにしました。
- 型検証（`npx tsc --noEmit`）、対象5ファイルのeslintは成功しました。DBへ接続しない合成データのChrome・WebKit（320px / 390px / 768px）で、共有・管理の間隔、展開前後の操作位置、リンクコピー・他アプリ共有・キャンセル・未対応時のコピー、管理から編集、下書きの共有非表示、閲覧者の管理非表示、フォルダの見出し、ストーリー切替と画像解除、投票追加・選択肢の追加と解除・入力保持、合成保存時の24時間期限と投票設定を確認しました。
- 証拠は公開対象外の `.contingency/ui-notes-posting/verification.json` と同フォルダ内の修正前後スクリーンショットです。外部通信・実ユーザーデータは使っていません。
- iOS PWA・Android実機、OS固有の共有パネル、実DBへの保存は未確認です。commit・push・デプロイは実施していません。本番反映は保留です。

## 共通UIの独立確認

同日、共通UI担当の最終差分も合成データで独立確認しました。マイページの仮画面に追加した目標入口がないこと、グラフの仮枠が174pxに対して新しいグラフ用スケルトンは703.5pxであること、ノート・投稿・予定のタブ仮枠36pxに対してガラスタブは48pxであること、大会目標の追加可否を全目標件数で判定すると旧種目の目標で現行種目の追加も止まることを報告しました。共通UI担当が修正しています。

修正後、Chrome・WebKitの320px / 390px / 768pxで、各タブ仮枠は48px、マイページのグラフは703.5pxで共通部品と一致しました。大会目標の入口は、未設定・旧種目だけ設定済みの場合に開き、現行種目を全件設定済み・種目未登録の場合に無効になります。2種目を選択して追加上限へ到達することと、閉じる確認から編集を続けたときに入力を維持することも確認しました。

サーバーレンダーの合成確認では、ガラスUIの状態、44pxの戻る操作、タブの選択面が初期HTMLに出ます。公開画面にも共通CSSを供給するため、共通UI担当がCSSの入口をルートlayoutへ移しています。検証結果は `.contingency/ui-notes-posting/root-review.json` と `ssr-verification.json` です。これは合成UI・共通部品の確認で、実機や本番全画面の確認を代替しません。
