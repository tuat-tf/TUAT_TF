# OB戦の導線・欠席・当日エントリーの改善案

2026-10-03 / Codex。オーナー依頼は対策の検討。範囲は入口と戻り先、操作の整理、DNS・欠席・当日追加の影響。実装・DB更新・本番反映は行わない。

## 調査と現状

既存の未コミット変更・未追跡資料を保持し、git pull --ff-onlyで最新化（Already up to date）。現行コードと最新のOB関係記録、未実装の組み分け簡素化案を照合した。

- ホームからの編集入口はプログラムの `?edit=mine`。`ObMyEntry` のフォームを閉じると `setEditing(false)` だけで、遷移先の「自分の登録」に残る。ページヘッダーは別にホーム固定の戻り先を持つ。フォームを閉じる操作とページを戻る操作で行き先が異なる。
- `ObMeetWorkspace` と運営のタブはローカルstateで、URLに現在位置を残さない。再読込み・履歴移動で文脈を維持しにくい。
- `MeetPerformance` はDNS/DNF/DQを保持するが、`ObEntry` に大会全体の欠席状態はない。懇親会の出欠は大会の欠席ではない。
- `reconcileObEvent` は追加者を未配置で追加し、取消者の既存配置・試技を保持する。追加機能自体はあるが、登録から配置まで一続きの操作になっていない。
- 公開プログラムと補助表の競技予定は主に `entry.events` から作る。競技記録側だけDNSにしても、この登録情報を読む表示・補助候補判定に反映されるとは限らない。
- `MeetHeatPlan` はDNSの枠を配置候補から除外する。DNSに元の組・番号が残ったまま新規参加者を同じ場所に入れられるため、現在の出走表と元の配置の区別が必要。
- 競技保存は種目のrevisionと名簿を検証する。別担当が編集中に出場者を追加すると、古い名簿による保存を拒否され得る。現在の案内は入力を控えて開き直す方式。
- エントリー・補助編集はOB戦担当、競技運営の保存はシステム管理に分かれている。簡素化案の担当ロール提案と現行権限を混同せず、運営担当が一連の作業をできる権限設計を別途確定する。

## 提案する操作と状態

### 入口と出口

ホームは本人の出場・補助予定と「登録を編集」「OB戦を見る」に整理する。ホームの編集はホーム上で全画面フォームを開き、保存・取消・戻るでホームへ戻す。OB戦内で開いた編集は元のタブ・種目・スクロールへ戻す。ブラウザ戻るも同じ扱いにし、未保存確認は共通部品を維持する。

OB戦の入口の名称は「OB戦2026」など大会名に統一し、プログラムという名称で登録・運営全体を包まない。本人向けは「自分の予定」「プログラム」、担当者には「当日運営」を追加。補助表は必要な場所から直接開けるようにし、管理タブの中でさらにタブを探す構造を減らす。タブ・種目をURLに保持し、内部の戻ると大会を出る操作を区別する。戻り先は検証済みの内部URLに限る。

### 欠席とDNS

大会全体の出欠、種目ごとの出場状況、競技結果、懇親会の出欠を独立して持つ。未受付を欠席とみなさない。種目のDNSだけで補助担当可能とは判定しない。

- 種目の欠場: 種目画面または人物画面から欠場を選ぶ。他種目と補助担当は保持する。
- 大会全体の欠席: 人物画面で欠席を選び、これから実施する出場と補助担当への影響を一覧表示して反映する。既に終了した種目の記録は書き換えない。
- 補助員欠席: 欠席者の担当を有効人数から除き、役職別の不足を表示する。同じ画面から代替者を選ぶ。過去の担当・変更者・変更時刻は履歴として残す。

欠場は削除で処理しない。公開出走表、本人予定、出場・補助表、候補判定、CSVが共通の状態判定を使う。欠席を取り消しても番号や補助担当を黙って復元せず、現在の割当との衝突を確認する。

### 当日の組・番号を保つ

組み分けの簡素化案の複数選択・移動・交換は採用候補。ただし「常に番号を詰める」「空の組を消して番号を詰める」は準備中に限定する。

出走表を公開・招集した後は組番号とレーンを固定する。DNSが出ても他の人の番号を変えない。空き枠の行をUIに出さず、担当者が追加者を選んだ後に配置可能な組を提示することは両立する。取消・DNSに元の配置を残す場合は、現在の有効配置との違いを明確にする。

組の準備中・確定／招集中・終了の状態と、記録の速報／確認済みを分離する。終了済みの組へ当日追加しない。確定後の番号変更は影響する出走表の差分を表示し、担当者が明示的に行う。

### 当日エントリー

「当日追加」で既存参加者を検索し、未登録者のみ氏名・区分を入力する。種目を選んだ後、未実施の組への配置まで同じ流れで行う。資格記録・懇親会回答は後で入力できる。重複候補が複数なら本人確認で選び、氏名だけで自動結合しない。

満員なら別の組・追加組を提示し、他の組や記録を作り直さない。登録だけできて未配置になった場合は明確に表示する。競技エントリーと配置を一括する操作はDBトランザクションで保存し、途中成功を成功表示しない。既存の個別登録も残し、未配置者数を当日運営から処理できる。

別端末による新規追加だけなら、既存の編集中データに追加者を未配置として取り込めるようにする。同じ人物の配置・結果を双方が変更した競合は自動で上書きせず、差分を表示する。最新revisionを無条件に差し替えて再保存する方式は使わない。

## 優先順位と合格条件

1. ホーム編集の出口、入口の名称、タブ・種目の位置保存を修正する。
2. 大会欠席・種目欠場・補助員不足を共通状態として扱い、公開後の組番号を保持する。
3. 当日追加から配置までの操作と、並行編集時の新規追加の取り込みを整える。
4. 組み分けの操作を既存簡素化案に沿って絞り、当日運営へ未配置・補助不足・未記録をまとめる。

検証例: ホームから編集して戻る／保存して戻る、OB戦内の種目から戻る、5レーンがDNSでも6〜8レーン不変、欠席者の過去記録保持と将来の補助不足表示、単一種目DNSで他種目を保持、満員の組への当日追加、終了済み組への追加拒否、二端末で記録入力中に追加、欠席取消と枠再利用の衝突、保存通信失敗と再試行による重複防止。スマホ実機・本番停止から復帰までの試験は別に確認する。
