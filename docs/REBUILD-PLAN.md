# 再構築設計案

作成: 2026-09-22 / 状態: Q1〜Q8回答反映。出力仕様・画面配置等は仮案

この文書は新版の計画であり、現行の機能廃止・データ削除・本番切替の指示ではない。質問への回答で更新する。実装日程と費用は範囲確定後に見積もる。

## 1. 目標と確定度

目的は、部員が迷わず入力・閲覧でき、少ない通信で動き、担当者とAIが維持しやすいアプリにすること。コード行数の削減そのものを目標にしない。

| 区分 | 内容 |
|---|---|
| ユーザーの方針 | 動画なし。現在70人・将来最大100人。無料優先で、必要なら非必須機能や更新頻度を減らす。現行の継続利用を守る |
| スプシ方針 | 記録・コメントはアプリ→スプシへ1日1回、既存形式を維持。中長距離メニューのみ従来どおりスプシ→アプリ。予定は手入力・同期なし |
| 技術候補、未採用 | React/Vite、Workers API、D1、非公開R2、Googleログイン |
| 未実証 | 全機能の無料運用、本番Cloudflareでの認証・CPU・画像処理・移行・iOS動作 |

根拠: [Cloudflare検証](CLOUDFLARE-FEASIBILITY-2026-09-22.md)、[アプリ入力検証](APP-ONLY-EVALUATION-2026-09-22.md)、[実測監査](AUDIT-2026-09-21.md)。過去の改善前の負荷を現在値として使わない。

## 2. 機能の整理案

初日必須は記録・つぶやき・コメント・予定・出欠・メニュー・大会・目標。Q5のホーム要望からお知らせも初期範囲に含める解釈とする（通知/投票の全機能を含む意味ではない）。「後続」は新アプリの初期実装を後回しにする提案であり、過去データを削除する決定ではない。過去データは全件閲覧・編集できる方針を希望。ただし本人/管理者等の既存権限は維持し、全員が全件編集できる意味にはしない。後続機能の履歴にも編集手段が必要なので、互換編集画面を用意するか初期範囲へ戻すかを切替前に解決する。

| 領域 | 現行で確認できる機能 | 新版案 | 時期・確認点 |
|---|---|---|---|
| ログイン・部員・権限 | Google認証、プロフィール、ブロック、ロール | 共通の認証と操作単位の権限判定 | 初期必須。現行の権限表を移植前に確定 |
| 練習記録 | 距離、自由記述、追加項目、編集 | アプリ内の項目定義と記録保存に統一 | 最初の実装対象 |
| 投稿 | 記録、つぶやき、一覧、個別リンク | 共通の投稿表示・編集枠。データ型の違いは保持 | 初期必須 |
| 反応 | いいね、コメント、共有 | 共通操作と表示、対象の閲覧権限に追従 | コメント初期必須。いいね・共有は確認 |
| 予定・出欠 | 月間入力、ブロック別予定、出欠一覧 | 予定・出欠はアプリで入力し、PC停止中も利用。同じ予定から月/一覧/出欠を表示 | 初期必須。予定変更時も出欠の紐付けを保持 |
| 練習メニュー | シート取得・編集 | 中長距離のみ従来どおりスプシを読取 | 初期必須。反映遅延・負荷・更新検知方法を検証 |
| お知らせ・投票 | 配信対象、対象者除外、アーカイブ、投票 | お知らせ画面に集約。投票は独立したデータとして保持 | お知らせ初期、投票は必要度確認 |
| 通知 | アプリ内通知、未読、Web Push | アプリ内通知を基準としPushは非同期配信 | アプリ内初期、Pushの初期必須性を確認 |
| 大会 | 大会一覧、プログラム、結果、目標 | 大会詳細にプログラム/結果/目標を集約 | 初期必須。自動速報の必要範囲を確認 |
| 個人記録 | PB、ランキング、走行距離、目標・過去目標 | 同じ集計ルールを部員/自分/ランキングで使用 | 目標初期必須。PB・ランキングは確認 |
| ノート | フォルダ、記事、写真、スレッド | ノート内に整理、投稿と操作部品を共有 | 初期必須か確認。公開範囲は保持 |
| その他 | ブログ、イベント、場所管理の画面 | 予定/ノート/設定との統合可否を個別判断 | 後続候補。名前だけで同一機能扱いしない |
| ゲーム等 | 履歴にito機能の記載 | 現行コード・稼働有無を再確認し別機能として判断 | 後続候補。現行ページ一覧では未確認 |
| 画像 | アイコン、投稿/ノート写真 | 共通アップロード・参照・削除管理 | 必要な種類と上限を確認。動画は対象外 |
| スプシ連携 | 取込、書戻し、列設定、返信照合 | 記録・コメントは日次出力、中長距離メニューのみ取込、予定同期なし。既存形式を維持 | 機能ごとに入力元を固定。予定は手入力 |
| 管理・保守 | 権限、マスタ、監視、バックアップ | 一つの管理画面、失敗状態と復元手順を明示 | 切替前必須 |

現行のsrc/appのページ、BottomNav、AGENTSの履歴に基づく棚卸し。ページ数は機能数や利用頻度ではない。次段階で各行に実際の利用者・頻度・移行テーブル・受入条件を紐付ける。

## 3. 画面構成とUIルール

下部ナビは「ホーム・予定・タイムライン・大会・自分」の5項目を新しい仮案とする。初期必須の大会に常設入口を設け、ノートは必須性を確認して配置を決める。目標は大会詳細と自分のページから同じ画面へ、お知らせはホームの見出しから一覧へ。名称・配置は試作で確認し未確定。

ホームは①今日の予定・出欠（メニューへの入口を一体化）②重要なお知らせ③開催中だけ大会の進行状況④最近の投稿を少数表示、を仮配置とする。大会カードの順位は試作で調整。各領域に「すべて見る」を設け、ホームと専用画面でカードや操作を変えない。タイムライン表示はQ5で任意の希望として受領。

Q6の問題は、装飾の多さだけでなく「場所が分からない」「同じ操作が違う形で出る」こと。シンプルさの基準を、主要機能の入口が文字で分かること、同じ動作のボタン位置・名前・入力方法が一致することとする。アイコンだけの隠れた入口を増やさない。初回利用者が記録入力・出欠回答・目標編集・大会結果閲覧へ案内なしで進めるか試作で検証する。

| 操作/状態 | 統一ルール案 |
|---|---|
| 一覧 | タイトル、検索、絞り込み、件数、一覧の順。長い一覧はページング。位置と絞り込みを戻る操作で保持 |
| 詳細 | 共有可能なURLを持つ。モバイルは詳細ページを基本とし、一覧内展開が必要な投稿は共通部品で対応 |
| 作成・編集 | 同じフォーム部品を使用。作成は「作成する」または「投稿する」、編集は「保存する」。保存中は二重送信を防止 |
| 長文入力 | モバイルは全画面編集。キーボード表示で操作が隠れない。Enterで勝手に閉じない |
| 編集・削除の入口 | 本人または権限者の「…」へ統一。ボタン非表示だけに頼らずAPIで権限を確認 |
| 未保存 | 戻る/閉じるで確認。可能な範囲で端末内下書きを保持し、他アカウントへ引き継がない |
| 保存成功 | DB確定後に入力画面を閉じ、対象の表示を更新。外部通知の完了を待たせない |
| 保存失敗 | 入力を保持し、原因と再試行操作を表示。結果不明の場合も重複作成しない |
| 削除 | 対象名と影響を表示して確認。アーカイブと永久削除を区別 |
| 読込・空・失敗 | 初回読込、0件、検索該当なし、権限なし、取得失敗を区別。更新失敗時に既存表示を消さない |
| 更新 | 自分の保存は即反映。他人の更新は必要な画面のみ。タブ非表示中は定期取得停止、手動更新を用意 |
| 見た目 | 色、文字、余白、角丸、入力、ボタン、ダイアログの共通定義。色だけで状態を伝えない |
| 操作性 | タップ領域は原則44px以上、キーボード操作とフォーカス表示、ラベルを用意。iOS safe-areaとスクロール固定を共通化 |

共通化するのは操作と表示の枠。出欠・大会結果・文章投稿を無理に一つの巨大フォームにしない。先に代表画面の試作を確認してから全機能に展開する。

## 4. データと実装構成

データの入力元は機能ごとに一つ。記録・コメント・出欠はアプリDB、予定はアプリDB、中長距離メニューはスプシを正とし、アプリの閲覧用データへ取り込む。シートの列名を記録項目の識別子にせず、安定した項目IDと版を持つ。名称変更後も過去の記録を再現する。日付、時刻、距離小数、競技結果の精度と欠場等の意味を保持する。

候補構成:

```text
ブラウザ → 静的UI
         → Workers API（認証・権限・入力検証）→ D1
                                           → 非公開R2（写真）
         保存時に通知予定を確定 → 非同期送信処理
```

認証ライブラリ、画像処理経路、通知の実行方式は適合試験後に確定。D1は認証やRLSの代替ではない。最新要望によりPC主体・停止時クラウド継続を検討。全履歴と重い処理はPC、最近の表示・新規受付・認証・予定等はクラウドに置く案。上図はクラウド側候補であり、全履歴をD1へ移す決定ではない。詳細は[PC併用設計](REBUILD-PC-FALLBACK.md)を参照。

コードは認証・記録・予定・通知・大会・ノートの単位に分け、UI共通部品とAPI契約を共有する。画面からDBへ直接アクセスしない。別機能の内部ファイルを参照する代わりに公開した関数/APIを使う。フレームワークやDB依存は各機能の保存層にまとめる。

各機能の短いREADMEに、仕様、入口、権限、データ、検証コマンドを記す。AGENTSには現在の運用ルールと文書索引を置き、長い作業履歴は別文書へ整理する案とする。過去の制約を捨てずに検索できる形で残す。

### 機能ごとに方向を固定したスプシ連携

最新訂正を優先し、記録・コメントはアプリ→スプシへ1日1回出力。予定はアプリで手入力し同期しない。中長距離メニューだけ従来どおりスプシを読み取る。短距離への取込は追加しない。以前の予定取込案は撤回。

中長距離メニューはPC停止中もクラウド側で読取可能にする案。既存の読取・キャッシュ仕様を確認し、取得を共有する。失敗時は最後の成功データと取得時刻を表示する。未検証の即時性を保証しない。

Google通信は残るため、同期全廃の削減値は適用しない。PCとの同期負荷も加えて検証する。

1. 記録保存と出力待ち状態をDBで一緒に確定し、画面は保存完了にする。
2. 別処理で変更分だけまとめて出力。同じ記録の連続編集は最新の版へまとめる。全員のCSV再取得を前提にしない。
3. 安定した記録IDと版で更新先を特定し、再送で行を増やさない。処理中の新しい編集を消さないよう、成功した版だけ完了扱いにする。
4. 失敗は回数上限と待ち時間を設け再試行。最終反映時刻・反映待ち・失敗を確認できるようにし、Google障害でもアプリの保存は継続。
5. 削除も出力対象とするが、行削除か削除表示かは未決。既存シートの数式・手入力欄を無断で上書きしない。

記録・コメントの出力頻度は1日1回。実行時刻は未定。コメントは対象記録と紐付け、記録を編集していなくてもコメントの追加・編集・削除を出力待ちとして追跡する。失敗翌日も未反映分を保持し、コメントIDと版で重複や古い内容への巻き戻りを防ぐ。

シート形式は現在と同様に反映する方針。既存の列配置・数式・コメント欄を調査し、対応関係を維持する。ユーザーに内部書式の再設計を求めない。そのため列対応の実装は残る。記録の逆方向取込は行わない案とし、出力先セルの手編集の扱いを明示する。メニューのリアルタイム反映は日次バッチと別経路にし、必要な遅延と負荷を検証する。

これは復元可能なDBバックアップとは別。権限・添付・出力状態等も含めたバックアップを維持する。実行方式は未採用であり、Google/APIの現行条件と負荷を確認してから決める。

## 5. 性能と運用の受入基準案

以下は現状の測定結果ではなく、開発時に判定する目標。対象端末・回線・人数を固定して測る。

- 基本記録の保存完了はp95で2秒以内を仮目標（写真アップロードは別測定）。失敗しても入力消失なし。
- ホームは代表的なスマホ回線で主要情報表示2.5秒以内を仮目標。初回/再訪を分ける。
- 一覧は初期30件を基準にし、全件取得を避ける。APIごとのDB読取行数・応答サイズ・外部通信・CPUを記録する。
- 現在70人、将来最大100人。練習日の午後の投稿集中と大会中の閲覧集中を別シナリオにする。100人登録と100人同時アクセスは区別し、同時数と投稿/閲覧頻度を測る。3万件は従来の合成条件であり全履歴件数の予測ではない。
- 無料枠の採用判断は、現行公式条件を再確認した上で、通常日だけでなくピーク日・再試行・監視・バックアップを含めて行う。通常の想定使用量は各上限の50%以下を設計目安にする。
- ログイン、本人編集、他人の更新拒否、非公開データ、権限取消、重複送信、同時編集を自動検証。iOS Safari/PWAの入力・戻る・キーボード・長文・スクロールは実機で確認。
- バックアップは取得だけでなく別環境への復元成功を切替条件とする。保持期間、復旧目標、通知先を確定する。

無料優先（Q4のB）。UI修正だけでは無料運用の成立を証明しない。上限に近づいた場合は、まずスプシ出力を遅らせ、非必須の自動更新を減らし、保存・出欠等の主要操作を優先する。硬い上限で主要機能まで止まる可能性は実測で判断し、無料と無停止を保証しない。勝手な有料化はしない。

## 6. 段階と完了条件

| 段階 | 成果物 | 次へ進む条件 |
|---|---|---|
| 0 範囲決定 | 本文と質問回答、機能優先度、権限表 | 初期版の必須機能と未対応機能の扱いが決まる |
| 1 UI試作 | ホーム、記録一覧、入力、詳細のスマホ試作 | 部員の主要な操作が迷わず完了する |
| 2 技術実証 | ログイン→記録作成→閲覧→編集、共通API、負荷測定 | 権限・iOS・本番相当実行制限を満たす。Cloudflare採否を確定 |
| 3 初期機能 | 優先機能、画像、必要な通知、管理/監視 | 受入テストと想定ピーク負荷に合格 |
| 4 移行リハーサル | データ変換、照合、復元、旧URL対応手順 | 件数だけでなくID・関係・本文・精度・非公開範囲が一致 |
| 5 限定試用 | 少人数が新アプリの別環境を使用 | 入力消失、権限違反、重大なUI不具合なし |
| 6 本番切替 | 最終移行、導線更新、旧環境退避 | 最終差分照合、停止/復帰手順と担当者が確定 |

期限は設定せず、現行アプリを継続利用できることを優先（Q7）。再構築のために現行のサービスを解約・停止しない。重大な障害の修正は続ける。新版の完成を理由に急いで切り替えない。切替時の短時間停止の許容範囲は未回答であり、別途決める。

限定試用の入力は原則合成/試験データとし、本番記録を二重管理しない。実データを使う場合は参照範囲と試験中の書込先を先に定義する。

本番切替は旧環境の書込を一時停止し、最終差分を移し、照合してから新環境を開く。新環境で書込が始まった後はURLだけ戻さず、新規分を回収・照合して復帰する。旧リンクは投稿ID等の対応を保ち、開けない機能は保存済みデータへの閲覧手段を用意する。Vercelをリダイレクト用に残す案は新URLと認証確認後に具体化する。

現段階で旧コードや旧DBを削除しない。検証済みの大会解析、距離・日付の扱い、権限仕様、回帰テストは再利用を評価する。
