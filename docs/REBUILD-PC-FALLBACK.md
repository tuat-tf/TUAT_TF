# PC主体・停止時クラウド継続の設計案

2026-09-22。ユーザーの最新要望を受けた設計案。実装・障害試験・無料枠適合は未検証。本番変更なし。以前のクラウド単独案に代わる検討対象。

## 要望と仮の範囲

- 基本はPCで処理し、全履歴を閲覧・編集する。
- PC停止中は直近3日分の入力を表示し、新規入力を受け付ける。
- 予定等はPC停止中も動く。予定はアプリで手入力、スプシ同期なし。
- 中長距離メニューだけ従来どおりスプシから読み取る。短距離への取込は追加しない。
- 記録・コメントは従来形式のスプシへ1日1回出力する。

確定: PC停止中も記録・つぶやき・コメント・出欠の入力を受け付ける（オーナー回答）。出欠は予定と一緒に常時利用可能にする。

未確定: 「3日」はJSTで今日を含む3暦日を仮案とする。「予定とか」のお知らせ・大会・目標の範囲、72時間との違い、停止中の既存投稿の編集/削除は確認が必要。全履歴を扱う方針は通常時の要件として維持し、停止中だけ閲覧範囲を限定する。

## 推奨する役割分担案

| 対象 | クラウド | PC |
|---|---|---|
| 入口・ログイン・部員/権限 | 常時稼働。新規ログイン/セッション更新もPC不要 | 認証済み操作を検証 |
| 予定・出欠 | 正本を常時保持し読取/更新 | 必要時の参照用コピー |
| 中長距離メニュー | シート取得と最後の成功データを保持 | PCが取れないと更新不能、という依存を作らない |
| 最近の投稿 | 直近3日表示に必要な本文・投稿者・コメント等を保持 | 全履歴の保存・通常時の取得処理 |
| 新規入力 | 操作ID付きで永続受付、最近の表示にも反映 | 未処理操作を取得し、重複なく適用 |
| 過去の履歴・重い集計 | PC停止中は利用制限を明示 | 主担当 |
| 画像 | 停止中に必要な画像はPC不要で取得できる保管先へ | 長期保管等を検討 |

構成上の重要な提案: 新規書込の入口は通常時もクラウドに一本化する。PC主体とは全履歴・重い処理をPCが担う意味であり、書込まで完全にPCだけで完結させる意味ではない。クラウドに入力を確実に残してから「保存しました」と返すことで、直後のPC停止でも受付済みの入力を守る。クラウドにも通信・書込コストが残る。この方式の採用は未確定。

PCとクラウドで別々に書込を受け、接続状況だけで切り替える方式は、通信断と応答消失時に二重受付・更新競合が起きる。単純なURL切替では成立しない。PCのみで受付後に後送する方式では未送信分を停止中に表示できないため、今回の要望に対する推奨案にしない。

## 受付・復帰の手順

1. クラウドAPIで本人/権限・入力を検証し、操作ID・対象ID・期待する版を付け、表示用データとPC向け未処理操作を同時に永続化。
2. PCは認証された同期経路から取得し、操作IDの一意制約で一度だけ適用。適用と受領記録を同じトランザクションで確定する。
3. PC適用済みの位置をクラウドへ応答。応答が失われても再送は安全に行える。クラウドは未処理操作を表示対象から落とさない。
4. 停止中はクラウドの最近の表示と受付を継続。PC復帰後も追いつくまでは縮小モードを維持し、適用位置とデータ整合を確認して通常表示に戻す。
5. 編集は期待する版を照合し、競合を黙って最終更新時刻だけで解決しない。削除は削除記録として同期し、古いコピーから復活させない。

予定等の正本は常にクラウドなので復帰時に正本を切り替えない。全アプリ操作は共通API経由とし、PC上DBへの直接編集を通常操作にしない。権限取消はクラウドで即時判定し、PCの古い権限コピーで許可しない。

## 3日保存で注意する点

- 表示期間と保管期間を分ける。PC未受領の入力は3日を過ぎても消さない。長期停止中のデータ量も計測する。
- 最後の稼働時点の3日分を固定表示するのか、現在からの3日なのかを確認する。仮案は後者。新規入力がなければ長期停止後に一覧が空になる場合がある。
- 過去日付の新規記録を許すなら受付日時と記録日を分けて管理し、保存したのに見えない状態を避ける。本人の受付済み一覧を設ける案。
- 古い投稿への新規コメントは対象本文・閲覧権限がクラウドにない場合がある。対象を保持するか停止中は制限するかを決める。
- 画像をPCだけに置けば本文だけ残っても写真は見えない。添付対応は別途範囲確定する。
- 通常時の過去データ編集もクラウドの操作記録に残すが、PCの対象版の確認が必要。停止中の過去データ編集は今回の必須範囲に含めず確認する。

## 障害検証と運用

必須試験: PC電源断、ルーター断、PC応答だけ消失、同じ操作の再送、停止中の新規ログインと出欠、復帰途中の再停止、複数端末編集、権限取消、日付境界、4日以上の停止、未処理入力の保持、画像取得、復元。

画面には「一部機能を制限中。新規入力は保存できます」と最終同期時刻を表示する。PCへの要求は有限のタイムアウトと連続失敗時の呼出抑止を設け、毎画面長時間待たせない。正常復帰には連続成功と追随確認を必要とし、接続が戻っただけで切り替えない。

クラウド自体が停止/上限到達した場合まで新規受付を保証する構成ではない。最近のDB容量が減っても、全新規書込の受付、認証、権限、予定、同期、監視のクラウド使用量は残る。月単位の件数・CPU・転送量、最大停止期間に応じた未処理容量を測り、クラウド単独案と比較する。従来のD1ローカル検証はこの障害復旧方式の検証にはならない。

追加の同期実装が必要なため、クラウド単独より運用とテストは複雑になる。無料枠の節約量がその複雑さに見合うかを小規模実証で判定する。PC側DB製品や接続方式はまだ固定しない。
