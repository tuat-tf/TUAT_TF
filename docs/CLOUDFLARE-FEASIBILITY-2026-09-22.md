## 3. 主要な移行判断

| 領域 | 判定 | 必要な変更 |
|---|---|---|
| 投稿・予定・出欠・目標 | 実現可能 | SQL/型変換、索引、ページング、共通API |
| 小数・配列・JSON | 変換が必要 | 距離は整数100分の1などで精度保持。配列は関連表/JSON、UUIDはTEXT、日時は統一したUTC表現。競技記録は既存精度を別途保持 |
| Googleログイン | 実現可能だが未実証 | D1はAuth製品ではない。対応ライブラリ選定、state/PKCE等、Cookie、失効、大学所属確認、既存Google subjectと部員UUIDの対応を検証。メールだけで無条件に紐付けない |
| 権限 | 最重要の移植箇所 | D1へPostgres RLSは持ち込めない。ブラウザからDBへ直接アクセスさせず、Workersの認証と共通権限判定＋所有者条件付きSQLで守る。全ロール組合せ・非公開ノート等を移行テストにする |
| DB関数/原子的更新 | 再設計 | 固定SQLのD1 batch、制約、revision比較を利用。外部HTTPとDB更新を同じトランザクションにできると考えない |
| スプシ連携 | 無料枠の主要リスク | 現行chunk既定100人・maxDuration 300秒。既に分割/変更検知はあるが、無料Workers向けに一回のCPU・query・外向き通信数を測り再分割。全量取込や名簿一括変更をそのまま移さない |
| 大会速報 | 解析の一部は再利用可 | 既存fixtureで解析一致。ただし本番HTMLの大きさとCPUは未測定。置換はbatchまたは世代を準備して公開版ポインタを原子的に切替 |
| 写真 | 要別検証 | avatar / note-image / tweet-imageの3経路が `sharp` に依存。Nodeネイティブ画像処理をそのままWorkersへ載せる計画は不可。クライアント圧縮＋サーバー検証、または適合する画像処理経路を選ぶ。EXIF/サイズ/形式/再エンコードの現在の保護を落とさない |

| バックアップ | 実装・運用確認が必要 | Free Time Travelは7日。別の保管先へのexportと復元リハーサル、秘密設定・R2画像との整合も必要 |

## 4. 無料枠の評価

公式条件（2026-09-22参照）: D1 Freeは1DB **500MB**、アカウント全体5GB、読取500万行/日、書込10万行/日。1SQL 100パラメータ、Freeでは1Worker呼出し50クエリ。1DBは順次処理のため、遅いSQLは同時利用にも影響する。[D1 limits](https://developers.cloudflare.com/d1/platform/limits/)、[pricing](https://developers.cloudflare.com/d1/platform/pricing/)

Workers Freeは10万request/日、HTTPもCronもCPU **10ms**。外部通信待ちとDB待ちはCPU時間に含まれないが、JSON/CSV解析・暗号処理・画像処理等は実行負担になる。Cronの長いwall time許可とCPU枠を混同しない。[Workers limits](https://developers.cloudflare.com/workers/platform/limits/)

### 仮定を置いた設計予算（本番予測ではない）

通常の画面APIとは別に2分ごとの通知確認、同期等313回/日、再試行の余裕20%を仮定。1APIの読取予算を200行、本人の保存20回/日・1保存あたり索引等込み5行書込と仮定する。同期の実書込、その他ジョブ、ボット、OAuth等が予算内かは未測定。

| ケース | 100人・通常API100回/人/日・表示60分 | 200人・通常API150回/人/日・表示120分 |
|---|---:|---:|
| Worker要求/日（余裕込み） | 15,976 | 50,776 |
| D1読取行/日（仮定200行/要求） | 3,195,200 | **10,155,200：無料枠超過** |
| 本人の保存によるD1書込行/日（余裕込み） | 12,000 | 24,000 |

小規模の日常利用なら予算に収める余地がある。一方、要求数が枠内でもDBの走査量で先に上限へ当たる。これらは実利用者数・実操作頻度の観測値ではない。3万件の軽い一覧検証だけで全機能の無料適合と結論しない。

写真はR2 Standardの容量・操作回数の別枠。動画なしでも写真とバックアップの増加を管理する。Workers Paidは月5ドルからだが従量分・R2・画像処理等は別であり、5ドルの総額上限ではない。[Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)、[R2 pricing](https://developers.cloudflare.com/r2/pricing/)

## 5. 推奨構成と採用条件

React/Viteの静的画面 → 同一サイトのWorkers API → D1。写真は非公開R2。旧Vercelは閲覧URLの転送のみ。本番はPCの電源/回線へ依存させない。Google/スプシ等の外部連携先の制限は残る。

**次の実装段階へ進んでよいが、完全無料を契約・運用前提にする判定は保留。**

1. Cloudflareの隔離した実環境で、正式な認証ライブラリを用いたGoogleログイン、既存部員ID対応、失効、ロール取消まで確認。
2. 通常の一覧/投稿に加えて最大に近い同期と写真処理を試す。CPU・requests・D1 rows_read/rows_written・レイテンシを記録。無料を目標とするなら、観測したp95 CPU 5ms以下を目安にし、最大入力でも10ms以内の余裕を検証する（p95だけで合格にしない）。
3. 代表的な1週間と大会のピークを模した負荷で日次枠の70%以下を目標にする。超過時は同期分割・更新頻度調整・画像経路変更を検討し、成立しなければ少額課金か仕様変更を判断する。
4. 全テーブル/権限/DB関数の移行対応表、実データ変換dry-run、復元手順を完成させる。本番の全データを今回の11表モデルで置き換えない。
5. 切替前に書き込み停止、最終差分移行、検証、再開。新側で書いた後に旧DBへURLだけ戻さない。Google callbackとPWA/SW/Pushの移転も確認。

今回の結論を「Cloudflareへ移すだけで軽くなる」「移行完了」「完全無料を実証」と扱わない。UIの作り直しや本番移行は今回行っていない。
